## 🎯 Design Philosophy

### Core Principles

1. **Simplicity Over Complexity**: Two core tables instead of dozens of stage-specific columns
2. **Audit-First Architecture**: Every status change creates a new row - no updates, only inserts
3. **Immutable History**: Complete processing timeline preserved for debugging and compliance
4. **Extensible Design**: New processing stages added without schema changes
5. **Query Performance**: Optimized indexes for common access patterns

### Key Design Decisions

- **Insert-Only Status Tracking**: Each status change gets its own timestamped row
- **Processing-Only Focus**: Document management and processing status only - content metadata handled by Knowledge Graph
- **Stage-Agnostic Processing**: Generic processing status table handles all pipeline stages
- **Referential Integrity**: Proper foreign keys with cascade deletes
- **JSON Flexibility**: JSONB fields for stage-specific metadata when needed

## 📊 Database Schema

### 1. Documents Table
**Purpose**: Core immutable facts about each document

```sql
CREATE TABLE documents (
    doc_id VARCHAR(32) PRIMARY KEY,
    source_url TEXT NOT NULL,
    original_filename TEXT,
    file_size_bytes BIGINT,
    file_hash VARCHAR(64),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Indexes
CREATE INDEX idx_documents_source_url ON documents(source_url);
CREATE INDEX idx_documents_created_at ON documents(created_at);
CREATE INDEX idx_documents_file_hash ON documents(file_hash);
```

**Field Descriptions:**
- `doc_id`: Unique 32-character identifier (generated by DocumentIDManager)
- `source_url`: Original source URL of the document
- `original_filename`: Filename from the source system
- `file_size_bytes`: Size of document file in bytes (for deduplication during repository rescans)
- `file_hash`: SHA-256 hash for deduplication and change detection during repository rescans
- `created_at`: When the document record was first created (original download date)
- `updated_at`: Last time document was encountered during repository rescans (not for processing updates)

### 2. Document Processing Status Table
**Purpose**: Audit trail of all processing stages and status changes

```sql
CREATE TABLE document_processing_status (
    id SERIAL PRIMARY KEY,
    doc_id VARCHAR(32) REFERENCES documents(doc_id) ON DELETE CASCADE,
    stage VARCHAR(50) NOT NULL,
    status VARCHAR(20) NOT NULL,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    error_message TEXT,
    system_id VARCHAR(100),
    retry_count INTEGER DEFAULT 0,
    metadata JSONB,
    
    -- Constraints
    CONSTRAINT valid_status CHECK (status IN ('pending', 'in_progress', 'completed', 'failed', 'skipped')),
    CONSTRAINT valid_stage CHECK (stage IN (
        'download',           -- Document downloaded from source URL
        'textract_initiate',  -- Textract job submitted
        'textract_complete',  -- Text extraction completed
        'chunking',           -- Document split into chunks
        'vector_embedding',   -- Vector embeddings generated
        'vector_indexing',    -- Vector embeddings indexed in OpenSearch
        'indexing',           -- Keyword search index to OpenSearch
        'nlp_initiate',       -- NLP Processing via comprehend initiated
        'nlp_complete',       -- NLP Processing via comprehend processed to datalake
        'kg_doc_structure',   -- Document Structure semantics added to Knowledge Graph
        'kg_entities',        -- Entities, etc. added to Knowledge Graph
        'validation'          -- Quality checks completed
    ))
);

-- Indexes
CREATE INDEX idx_processing_doc_stage_time ON document_processing_status(doc_id, stage, timestamp);
CREATE INDEX idx_processing_stage_status_time ON document_processing_status(stage, status, timestamp);
CREATE INDEX idx_processing_timestamp ON document_processing_status(timestamp);
CREATE INDEX idx_processing_system_id ON document_processing_status(system_id);
CREATE INDEX idx_processing_status_pending ON document_processing_status(status, timestamp) 
    WHERE status IN ('pending', 'in_progress');
```

**Field Descriptions:**
- `id`: Auto-incrementing primary key
- `doc_id`: Reference to parent document
- `stage`: Processing stage identifier (see enumeration)
- `status`: Current status of this stage (see enumeration)
- `timestamp`: When this status was recorded
- `error_message`: Details if status is 'failed'
- `system_id`: External system identifier (e.g., Textract job ID)
- `retry_count`: Number of retry attempts for this stage
- `metadata`: Stage-specific data in JSON format

## 🔄 Processing Flow Examples

### Typical Document Processing Lifecycle

```sql
-- 1. Document discovered and registered
INSERT INTO documents (doc_id, source_url, original_filename, file_size_bytes) 
VALUES ('abc123def456', 'https://example.com/report.pdf', 'climate-report-2024.pdf', 2048576);

-- 2. Download initiated
INSERT INTO document_processing_status (doc_id, stage, status) 
VALUES ('abc123def456', 'download', 'in_progress');

-- 3. Download completed
INSERT INTO document_processing_status (doc_id, stage, status) 
VALUES ('abc123def456', 'download', 'completed');

-- 4. Textract job submitted
INSERT INTO document_processing_status (doc_id, stage, status, system_id) 
VALUES ('abc123def456', 'textract_initiate', 'in_progress', 'textract-job-789xyz');

-- 5. Textract completed successfully
INSERT INTO document_processing_status (doc_id, stage, status, system_id) 
VALUES ('abc123def456', 'textract_initiate', 'completed', 'textract-job-789xyz');

-- 6. Text extraction results processed
INSERT INTO document_processing_status (doc_id, stage, status) 
VALUES ('abc123def456', 'textract_complete', 'completed');

-- 7. Chunking initiated
INSERT INTO document_processing_status (doc_id, stage, status) 
VALUES ('abc123def456', 'chunking', 'in_progress');

-- 8. Chunking failed (example)
INSERT INTO document_processing_status (doc_id, stage, status, error_message, retry_count) 
VALUES ('abc123def456', 'chunking', 'failed', 'Timeout during text processing', 1);

-- 9. Chunking retry
INSERT INTO document_processing_status (doc_id, stage, status, retry_count) 
VALUES ('abc123def456', 'chunking', 'in_progress', 2);

-- 10. Chunking completed on retry
INSERT INTO document_processing_status (doc_id, stage, status, retry_count) 
VALUES ('abc123def456', 'chunking', 'completed', 2);
```


## 🔍 Common Query Patterns

### Current Status Queries

**Get latest status for each stage of a document:**
```sql
SELECT DISTINCT ON (stage) 
    stage, status, timestamp, error_message, retry_count
FROM document_processing_status 
WHERE doc_id = 'abc123def456' 
ORDER BY stage, timestamp DESC;
```

**Find documents currently being processed:**
```sql
SELECT DISTINCT doc_id, stage, timestamp, system_id
FROM document_processing_status dps1
WHERE status = 'in_progress'
  AND NOT EXISTS (
    SELECT 1 FROM document_processing_status dps2 
    WHERE dps2.doc_id = dps1.doc_id 
      AND dps2.stage = dps1.stage 
      AND dps2.timestamp > dps1.timestamp
  )
ORDER BY timestamp ASC;
```

**Documents stuck in a specific stage:**
```sql
SELECT doc_id, timestamp, system_id, error_message
FROM document_processing_status dps1
WHERE stage = 'textract_initiate' 
  AND status = 'in_progress'
  AND timestamp < NOW() - INTERVAL '2 hours'
  AND NOT EXISTS (
    SELECT 1 FROM document_processing_status dps2 
    WHERE dps2.doc_id = dps1.doc_id 
      AND dps2.stage = dps1.stage 
      AND dps2.timestamp > dps1.timestamp
  );
```

### Analytics Queries

**Processing stage statistics:**
```sql
SELECT 
    stage,
    status,
    COUNT(*) as count,
    AVG(CASE WHEN status = 'completed' THEN retry_count END) as avg_retries
FROM document_processing_status 
WHERE timestamp >= NOW() - INTERVAL '24 hours'
GROUP BY stage, status 
ORDER BY stage, status;
```

**Document processing duration analysis:**
```sql
WITH stage_durations AS (
    SELECT 
        doc_id,
        stage,
        MIN(timestamp) as start_time,
        MAX(timestamp) as end_time,
        MAX(timestamp) - MIN(timestamp) as duration
    FROM document_processing_status 
    WHERE timestamp >= NOW() - INTERVAL '7 days'
    GROUP BY doc_id, stage
    HAVING COUNT(DISTINCT status) > 1  -- Only stages that completed
)
SELECT 
    stage,
    AVG(duration) as avg_duration,
    PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY duration) as median_duration,
    MAX(duration) as max_duration
FROM stage_durations 
GROUP BY stage 
ORDER BY avg_duration DESC;
```

## 🚀 Migration Strategy

### From Current Schema

1. **Phase 1: Create New Tables**
   - Deploy new schema alongside existing tables
   - Update DocumentIDManager and DatabaseManager to use new schema
   - Test with subset of documents

2. **Phase 2: Data Migration**
   - Migrate existing document records to new `documents` table
   - Convert existing status columns to `document_processing_status` rows

3. **Phase 3: Application Updates**
   - Update all Lambda functions to use new schema
   - Modify query patterns in application code
   - Update monitoring and alerting queries

4. **Phase 4: Cleanup**
   - Remove old tables after validation
   - Update documentation and procedures
   - Archive old schema for reference

### Migration Scripts

**Document migration:**
```sql
-- Migrate core document data
INSERT INTO documents (doc_id, source_url, original_filename, created_at)
SELECT doc_id, url, original_filename, created_at 
FROM legacy_documents;
```

**Status migration:**
```sql
-- Convert textract status to processing status rows
INSERT INTO document_processing_status (doc_id, stage, status, timestamp, system_id)
SELECT 
    doc_id,
    'textract_initiate',
    CASE 
        WHEN textract_status = 'SUCCEEDED' THEN 'completed'
        WHEN textract_status = 'FAILED' THEN 'failed'
        WHEN textract_status = 'IN_PROGRESS' THEN 'in_progress'
        ELSE 'pending'
    END,
    textract_started_at,
    textract_job_id
FROM legacy_documents 
WHERE textract_status IS NOT NULL;
```

## 🔧 Performance Considerations

### Indexing Strategy

1. **Primary Access Patterns**: Indexes optimized for document lookup and status queries
2. **Composite Indexes**: Multi-column indexes for common query combinations
3. **Partial Indexes**: Filtered indexes for active processing states
4. **JSON Indexes**: GIN indexes on JSONB metadata fields when needed

### Query Optimization

1. **Status Queries**: Use `DISTINCT ON` for latest status per stage
2. **Time-Range Queries**: Leverage timestamp indexes for recent activity
3. **Batch Operations**: Use `EXISTS` subqueries for efficient filtering
4. **Document Lookups**: Optimize queries by doc_id and source_url patterns

### Scaling Considerations

1. **Partitioning**: Consider time-based partitioning for processing status table
2. **Archiving**: Archive old processing status records after retention period
3. **Read Replicas**: Use read replicas for analytics and reporting queries
4. **Connection Pooling**: Implement proper connection pooling for high concurrency

## 📈 Monitoring & Observability

### Key Metrics

1. **Processing Throughput**: Documents processed per hour by stage
2. **Error Rates**: Failed processing attempts by stage and error type
3. **Processing Latency**: Time spent in each processing stage
4. **Queue Depth**: Number of documents pending in each stage
5. **Retry Patterns**: Frequency and success rate of retries

### Alerting Thresholds

1. **Stuck Documents**: Documents in 'in_progress' state > 2 hours
2. **High Error Rates**: > 10% failure rate for any stage in 1 hour
3. **Queue Buildup**: > 100 documents pending in any stage
4. **Processing Delays**: Average processing time > 2x historical average

### Dashboard Queries

**Real-time processing status:**
```sql
SELECT 
    stage,
    COUNT(CASE WHEN status = 'pending' THEN 1 END) as pending,
    COUNT(CASE WHEN status = 'in_progress' THEN 1 END) as in_progress,
    COUNT(CASE WHEN status = 'completed' THEN 1 END) as completed,
    COUNT(CASE WHEN status = 'failed' THEN 1 END) as failed
FROM (
    SELECT DISTINCT ON (doc_id, stage) doc_id, stage, status
    FROM document_processing_status 
    WHERE timestamp >= NOW() - INTERVAL '24 hours'
    ORDER BY doc_id, stage, timestamp DESC
) latest_status
GROUP BY stage
ORDER BY stage;
```

## 🔒 Security & Compliance

### Data Protection

1. **Document Management Focus**: Only operational processing data stored, no document content or content metadata
2. **Access Control**: Row-level security policies for multi-tenant scenarios
3. **Audit Logging**: All database changes logged for compliance
4. **Encryption**: Data encrypted at rest and in transit

### Retention Policies

1. **Processing Status**: Retain detailed status for 90 days, summary for 1 year
2. **Document Records**: Retain indefinitely unless document explicitly deleted
3. **Error Logs**: Retain error details for 180 days for debugging
4. **System IDs**: Retain external system references for audit trail
