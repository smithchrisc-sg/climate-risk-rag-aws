# DocumentIDManager Integration Fix - Migration Strategy
## Date: 2025-07-04T21:00:00Z

## 🚨 **Critical Issue Identified**

During TextExtractor Processor updates, discovered that the system was not properly integrated with the existing DocumentIDManager. The POC system uses a complete flow (PDF Download → DocumentIDManager → Processing), but we jumped to step 2 (text extraction) without the foundational DocumentIDManager registration.

## 📋 **Problem Analysis**

### **Normal POC Flow**
```
1. PDF Downloader → DocumentIDManager.get_or_create_id(url) → doc_id (GUID)
2. Text Extractor → Uses existing doc_id from database
3. Chunker → Uses doc_id for processing
4. All processors → Consistent doc_id throughout pipeline
```

### **Current Broken Flow**
```
1. [MISSING] PDF Downloader step
2. Text Extractor → Creates doc_hash, no doc_id connection
3. Chunker → Expects doc_id but gets doc_hash
4. System disconnect between DocumentIDManager and TextExtractor
```

### **Root Cause**
- **POC System**: Complete pipeline with URL → doc_id registration
- **Current System**: Started at step 2 without foundational doc_id setup
- **Business Reality**: Don't want to build PDF downloader right now

## 🎯 **Recommended Solution: SQLite → PostgreSQL Migration**

### **Strategy Rationale**
- **Preserves POC work**: All existing document processing maintained
- **Quick implementation**: Hours vs. days/weeks for PDF downloader
- **Data consistency**: Maintains URL → doc_id relationships from POC
- **Business focus**: Concentrates on RAG functionality vs. infrastructure

### **Migration Approach**
```python
# Command-line utility: migrate_poc_to_postgres.py
1. Read POC SQLite database (/Volumes/G-RAID Photo 24TB/climate_risk_rag/db/corpus_document_ids.db)
2. Extract documents table (doc_id, url, metadata)
3. Populate PostgreSQL documents table via DocumentIDManager
4. Create S3 → doc_id mapping for TextExtractor integration
5. Update TextExtractor to use existing doc_ids
6. Maintain doc_hash for job tracking compatibility
```
